# Operations Analytics Dashboard interview walkthrough

### Español 60 segundos
Este proyecto demuestra cómo convertir datos operativos en una herramienta de seguimiento y priorización. Python genera datos sintéticos, SQL calcula indicadores y un dashboard web permite comparar regiones, ver tendencias y revisar incidencias. La demostración incluye 120 activos ficticios durante 90 días. Cuidé especialmente las definiciones: la completitud se calcula con intervalos recibidos y esperados, evitando promediar porcentajes que podrían inducir a error. También incorporé una caída de cobertura para comprobar que se identifica visualmente. El proyecto conecta mi experiencia en analítica operativa con una evidencia pública que se puede explorar. Los datos son ficticios y el repositorio es una nueva demostración de portafolio; no es un sistema ni código de mi anterior empresa.

### English 60 seconds
This project shows how to turn operational data into a monitoring and prioritisation tool. Python generates synthetic observations, SQL calculates the metrics and a web dashboard lets users compare regions, explore trends and review exceptions. The demonstration covers 120 fictional assets over 90 days. I focused on metric definitions: completeness uses received and expected intervals, avoiding misleading averages of percentages. An injected coverage drop makes it possible to check the investigation workflow visually. The project connects my operational analytics experience with public evidence that a recruiter or technical interviewer can explore. The dataset is fictional and the repository is a newly built portfolio demonstration, not a system or source code from my former employer.

### Español Guion técnico de 5 minutos
Minuto 1 — Abro la demo y explico la decisión: qué activos o proveedores conviene investigar cuando baja la disponibilidad o calidad de lecturas. Selecciono South para mostrar que indicadores, gráficos y cola responden al mismo filtro.
Minuto 2 — Explico el grano activo por día, la clave única y los límites de los intervalos. El generador crea todos los activos y días; por eso puedo distinguir ausencia de lecturas de ausencia de registros. Cada dato y proveedor es ficticio.
Minuto 3 — Abro el SQL: completitud es suma de recibidos dividida por suma de esperados; validez es recibidos válidos entre recibidos. La ventana de indicadores cubre siete días y la tendencia 90. Si no hay recibidos, la validez es nula, no 100%.
Minuto 4 — Muestro la caída sintética South/Beta y la regla de revisión: menos de 90% de completitud o más de 2% de intervalos inválidos. Una bandera no diagnostica una avería. Las comparaciones de proveedores tampoco están ajustadas por composición de activos.
Minuto 5 — Ejecuto las pruebas de denominadores, restricciones y coherencia entre JSON y HTML. El dashboard es una instantánea estática: el proceso falla si detecta un HTML desactualizado. Cambiar los datos exige regenerar la presentación con el exportador externo y revisarla. El siguiente paso sería parametrizar fechas y añadir comparación con el período anterior.

### English Five minute technical walkthrough
Minute 1 — Open the demo and frame the decision: which assets or providers require investigation when reading availability or validity deteriorates. Select South to show that metrics, charts and the queue use the same filter.
Minute 2 — Explain the asset-day grain, unique key and interval bounds. The generator creates every asset and day, so missing readings can be distinguished from missing records. Every asset and provider is fictional.
Minute 3 — Open the SQL. Completeness is summed received intervals divided by summed expected intervals; validity is valid received intervals divided by received intervals. KPI cards use seven days, while the trend spans 90. Zero received intervals produce null validity rather than 100%.
Minute 4 — Show the synthetic South/Beta outage and the review rule: below 90% completeness or above 2% invalid intervals. A flag does not diagnose a fault. Provider comparisons are not adjusted for asset mix.
Minute 5 — Run denominator, constraint and JSON/HTML parity tests. The dashboard is a static snapshot: stale presentation data blocks the verification workflow. Changed data requires the external canonical exporter and a reviewed presentation. The next step would be configurable dates and prior-period comparisons.
